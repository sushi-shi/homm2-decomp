# B48: remote adventure-control selection

`ComputeAdvNetControl`, RVA `0x13a54`, has two distinct state hazards.
Its entire249-byte body, all absolute sites and ordered targets match genuine
retail (`build/b48-netcontrol-retail.log`).

When the current player is dead, the first loop initializes `player` to the
immediate successor but never advances it. If that successor is not a living
human player, the loop repeatedly tests the same index. Retail's `eb c1` at
function offset `+0x8b` jumps back to `+0x4e`; there is no intervening store
to the candidate at `[ebp-0xc]` and no callback that advances it.

The second loop initializes the same successor, increments it *before* the
eligibility test, and thus skips that immediate successor while testing the
current player at the end. If none of the tested candidates qualifies,
`selected` remains `-1`. At `+0xe8`, `0f be 88 …` reads the byte table
`gbThisNetHumanPlayer` with that unchecked index (owner relocation at `+0xeb`).

These conclusions are from the complete body and branch/data flow, not a
runtime multiplayer reproduction. Whether the protocol excludes particular
states remains a separate caller contract. The first missing increment is a
control-flow observation beyond the ten checklist categories; the possible
negative table index directly belongs to the bounds/out-of-object review.

Disposition: preserve and report genuine behavior. Adding an increment,
changing candidate order, or inventing a fallback player would be a behavior
change, not a byte-neutral reconstruction cleanup.
