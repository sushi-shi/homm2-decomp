# B37: modem initialization is used as a format string

The normal modem setup path passes `gConfig.modemInitString` as the format
argument to `sprintf`, with no formatting arguments. This is genuine retail,
not a mistaken reconstruction of a literal-format copy:

```
00472d56 68 8e 62 52 00  push 0052628e ; gConfig + 0xae, modemInitString
00472d5b 8d 45 98        lea eax,[ebp-68h] ; command[104]
00472d5e 50              push eax
00472d5f e8 da 40 06 00  call 004d6e3e ; sprintf
00472d64 83 c4 08        add esp,8
```

The field is declared100 bytes and is editable through `SetupComPort`'s
40-byte data-entry scratch. The data-entry handler zeroes the requested
capacity and copies at most capacity-1 bytes, so the setup copy into the100-byte
field is bounded. That does **not** bound `sprintf`'s interpretation of format
directives or make missing formatting arguments valid. The registry path also
populates the field.

`check-function.py SOURCE/Modem 0x72ca0` proves all504 bytes, complete DIR32
sites and ordered call/data/string targets against hash-verified genuine
retail (`build/b37-setup-retail.log`). Replacing this with `strcpy` or a literal
format would change the retail call sequence/behavior; no such change was
silently applied in this reconstruction audit.

Other modem bounds are separate and mostly proven: the terminated36-byte
telephone owner plus `ATDT` prefix fits its40-byte dial command, the fixed
RING/CONNECT strings fit the80-byte response buffers, and six-digit handshake
IDs/stage text fit their20-byte message. Nonnegative payloads up to256 bytes
escape to at most516 bytes. Negative generic payload lengths and the modem's
smaller transport limit remain B37/B41 caller-contract questions.
