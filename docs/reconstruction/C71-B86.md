## B86: real records, initialization and formats

Update reads one genuine packed 100-byte HighScoreEntry per iteration, ten
times. Its 17-byte player name, 41-byte scenario name and 29 reserved bytes are
actual serialized fields, not padding introduced to match the stack. This
reader does not repeat AddScoreToHighScore's whole-array read (B53), but ignores
read results: a short/error/empty file can leave some or all fields uninitialized
or stale from the previous record. When opening fails, it initializes only
score=-1 and later reads cheated unconditionally, even for empty rows. The
fixed instruction checker pins the score store and separate cheated-byte load.

For nonempty rows, both names are passed directly as sprintf formats with no
additional arguments. Ordinary percent-free terminated names fit gText, but
neither the reader nor the reviewed AddScoreToHighScore writer validates format
directives. A short, terminated name containing a conversion is therefore not
covered by a simple string-length bound. Malformed records also need explicit
termination. These are retail facts, not reasons to enlarge the record or
silently replace the calls with `%s`. The unconditional cheat suffix and
repeated empty-format calls likewise remain as emitted.

The constructor's Random(0,17) initializes all ten animation indices. Main and

than subscripting with them, including its standard-table fallback. Its full
