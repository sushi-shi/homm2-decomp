# B45: adventure text owners and decimal-label capacity

`HeroQuickView`, RVA `0xc322`, allocates five bytes for an exact troop-count
label and formats a signed16-bit count with `%d`. This is retail behavior,
not an inferred oversized stack slot. Native and retail agree on this span:

| Function offset | Bytes / target | Meaning |
| --- | --- | --- |
| `+0x592` | `6a 05` | request5 bytes |
| `+0x594` | `e8 …`, target `0x004d6a3b` | operator new |
| `+0x5b8` | `0f bf 54 41 6a` | sign-extend troop-count word |
| `+0x5be` | `68 …`, target `0x004efd08` | `%d` plus terminator |
| `+0x5cb` | `e8 …`, target `0x004d6e3e` | `sprintf` |

Positive counts10000..32767 require six bytes including NUL; signed minimum
needs seven. No local clamp or abbreviated format protects this allocation.
The army's real count field is `i16`; `armyGroup::Add` also has no9999 cap.
This establishes the capacity hazard, not a claim that a particular save/map
has been executed to reproduce corruption.

`check-function.py SOURCE/ADVMGR 0xc322` finds all3579 instruction bytes and
ordinary targets identical. Its unrelated EH/FS pseudo-relocation aliases are
unresolved, so this is not an independent whole-function closure claim.
[The scoped checker](check-advm-bounds.py) passes every byte and ordered target
in `+0x592..+0x5d3`, including the allocation size, signed load, actual format
bytes and `sprintf` call. See `build/b45-heroquick-retail.log` and
`build/advm-bounds-supplement.log`.

Other reviewed owners have different bounds:

- `GetArmySizeName`'s12-byte global holds any decimal32-bit signed integer,
  including its sign and NUL.
- The genuine9×3 army-name pointer table at `0x004ff148` has a maximum text
  length of9 bytes, or7 in the title column. Hero/town vague15-byte labels
  therefore fit those titles and the debug decimal return.
- Town exact-count15-byte labels fit all signed16-bit counts; its20-byte
  unknown-army label fits the fixed localized text.
- The bottom-view30-byte date labels fit their actual unsigned16-bit date
  fields. The month/week worst case uses28 bytes including NUL.
- Control-panel confirmation literals need at most72 bytes including NUL and
  fit their200-byte local. Full633-byte callback/relocation proof passes.
- Visions' five message arms need at most84 bytes including NUL even allowing
  arbitrary signed32-bit decimal arguments. Its66-entry genuine plural-name
  table has maximum21-byte text; the entire composed message needs at most121
  bytes including NUL, within `gText[768]`. The supplementary checker verifies
  these data bounds. The full body checker still leaves three unrelated
  floating-constant aliases unresolved; no whole-function closure is claimed.

Remaining B45 questions are separate: quick-info lookup strings used as
formats, `sprintf(gText, GetTownName(...))`, bottom-view message text used as
a format,92-byte incoming message copies,8-byte resource quantities/balances,
and negative troop counts in the bottom-view6-byte label.

Disposition: do not enlarge a retail allocation or replace its formatter as
a purported byte-neutral reconstruction. Keep the real owner and explicit
capacity hazard; behavior-changing remediation would be a separate patch.
