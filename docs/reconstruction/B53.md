# B53: high-score reads request the whole array at every record

`AddScoreToHighScore` (`0x0046bb0e`) has ten packed 100-byte
`HighScoreEntry` records. Its existing-file loop advances the destination by
100 bytes but requests 1000 bytes on every iteration. This is retail behavior,
not evidence for enlarging the reconstructed array.

Independent checking against the pinned genuine executable passes all 1029
function bytes, all DIR32 sites, and every ordered relocation target
(`build/b53-score-retail.log`). The current source emits the same operations:

| Function offset | Retail and current VC6 instruction | Meaning |
| --- | --- | --- |
| `+0x105` | `83 bd 00 fc ff ff 0a` — compare index with 10 | Ten iterations |
| `+0x10e` | `68 e8 03 00 00` — push `0x3e8` | Request 1000 bytes |
| `+0x119` | `6b d2 64` — multiply index by `0x64` | 100-byte record stride |
| `+0x11c` | `8d 84 15 04 fc ff ff` | Destination: array base plus stride |
| `+0x12b` | `e8 …` — call `_read` | Actual read target `0x004d8950` |

The ordinary writer emits ten **100-byte** records. Given a complete regular-file
first read of its canonical 1000-byte output, the first iteration fills the
array and the remaining nine reads encounter EOF. That case does not overrun.
An oversized file can overrun: after an initial 1000-byte read, iteration one
has only 900 destination bytes remaining. A second read above 900 bytes crosses
the array end. Partial reads and errors are ignored; short input can also leave
record fields uninitialized, and later reads are placed by record index rather
than accumulated byte count.

Keep the actual record and array extents. Its 29 reserved bytes are real
serialized bytes, not fake stack padding. Bounds remain open for malformed or
short files, player-name termination, and the unbounded scenario-name copy into
41 bytes. No byte-changing hardening or speculative storage expansion is applied.
