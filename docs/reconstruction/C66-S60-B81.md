# PATH: casts, unused storage and adjacency domains

All twelve physical definitions and the complete 638-line parent TU were read,
including its private constants and trailing compiler-generated markers. Parent:
`2b905597`. The existing direction/army/manager owners and `ValidHex` were also
checked. This is a King's Field checklist review, not a gameplay-hardening change.

## Applied C66 and measured S60

`army::FindPath` saves the signed-byte monster speed in an `i32`, temporarily
sets it to 99 when requested, then restores it after either search attempt.
Assignment to the real signed-byte member already performs the required narrowing:

```cpp
// Before
m_monster.speed = static_cast<i8>(savedSpeed2);
// After
m_monster.speed = savedSpeed2;
```

The complete two-arm C66 product preserves all 269 bytes and ordered relocations.
The saved value is originally loaded from this same `i8`; no overflow guard or
speed-policy change is introduced. The unnamed third argument is genuinely
unused by the implementation, not an invented scratch owner.

S60 tests deleting `i32 H2_UNUSED(extra)` from `army::ValidPath`. Both arms are
128 bytes with the same normalized relocation hash and eight diagnostic blocks,
but their text hashes differ. The original declaration is retained. An unchanged
block partition is not proof of identical instructions, and an unread source
local does not justify inventing a padding array to reproduce its frame effect.
No claim is made that deletion cannot match under any other structural parent or
compiler state.

Both independent products ran to completion and restored their input. The exact
source arms, elapsed times, hashes and topology are preserved in
[the measured source record](../matching/PATH/cast-and-unused-local.cpp).
No TU-state census was needed for the byte-neutral accepted change; these two
products are not a full source/state Cartesian search.

## B81: real owners and input contracts

The adjacency owner is `m_adjacency[117][6]`, not a flat scratch region or an
eight-direction physical row. The two additional logical attack directions
6 and 7 are converted to one of the six actual neighbor directions before
indexing. Army-dependent conversion uses facing; the no-army helper maps them
to northwest and southwest. Replacing the input direction with its corresponding
ordinary direction is related computation, not unrelated variable reuse.

The helpers special-case only source hex -1. They do **not** validate arbitrary
source indices or directions. After special-direction conversion, the contract
is source 0..116 and direction 0..5; negative direction -1 or arbitrary hex
values are not made safe by the sentinel test. Retail and candidate both use
the six-byte stride and signed-byte read from the same owner offset:

```asm
; army::GetAdjacentCellIndex, function-relative +0x4f..+0x66
; Candidate and retail agree (gpCombatManager relocation separately checked).
8b 4d 08                mov ecx, [ebp+8]
6b c9 06                imul ecx, ecx, 6
8b 55 0c                mov edx, [ebp+0xc]
03 d1                   add edx, ecx
a1 <gpCombatManager>    mov eax, [gpCombatManager]
0f be 84 10 ad f5 00 00 movsx eax, byte ptr [eax+edx+0xf5ad]
```

`ValidHex` explicitly accepts 0..116. `ValidMove` and `ValidAttack` validate
their source and computed destination before hex-cell access, but still require
a valid direction at the intervening adjacency lookup. `ValidAttack` also
requires a writable output pointer. Its early failure can leave that output
unchanged, or can leave a computed invalid hex there; success guarantees a
validated hex matching the requested occupancy mode. `GetAttackMask` passes a
real scalar output and never reads its value, so that local is meaningful
callee output storage, not an unused fake aggregate.

`GetMoveMask` iterates six directions; `GetAttackMask` iterates six or eight,
depending on width. Their single-bit values remain within the low eight bits;
the final shift to 256 is still representable. A side mask, facing, target mode
or manager pointer is not validated merely because it has a reconstructed enum
type. Drawbridge checks use the actual fixed gate/approach cells.

`ValidRange` validates the target but relies on live front/rear placement for
`m_hex` and the wide unit's `m_hex +/- 1`. Chained neighbor -1 is handled by the
helper's sentinel return. With valid endpoints and the fixed `0xc0` blocked mask,
`GetBestDirection` has an available ordinary direction; arbitrary malformed
placement is not thereby covered. The asymmetry between left/right early returns
and the ordered directional preferences is preserved exactly.

`GetBestDirection` validates both endpoints, then uses bounded quotient/remainder
coordinates and eight fixed mask bits. An all-blocked mask returns -1. Equal
source and target enter the no-horizontal/up-false fallback, rather than receiving
a new no-movement early return. It contains ordinary early returns, no goto,
temporary lookup array or synthesized owner arithmetic.

`OppositeDirection` implements `(direction + 3) % 6` for values below 6 and
exchanges 6/7 otherwise. It does not validate an arbitrary integer masquerading
as a direction; in particular the invalid sentinel -1 becomes 2. This is retained
retail behavior, not evidence that an invalid direction is a supported input.

Search allocation, combat side/army placement, facing and return/path-length
contracts remain inherited from their owners and callers. PATH does not access
the U02 path/pointer overlay directly and does not close that separate finding.
No normal-gameplay invalid-index reachability is asserted by these source-domain
observations. No buffer or guard is enlarged/added to hide them.
