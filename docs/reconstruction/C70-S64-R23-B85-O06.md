## B85: two actual retail index anomalies

`CampaignInfoUpdate` iterates13 track points but first reads the real2x12
`m_campaignMapEnabled` array. Its later `mapIndex<11` test does not guard that
load. Index12 reads side1's first byte when viewing side0; when viewing side1
it reads the low byte of `m_campaignScore` at game+0xba. Both leave their
selected inner array, and the latter also leaves the outer enabled array.
The genuine2x13 track-coordinate table is a different owner: widening the
enabled array would shift subsequent fields and contradict retail stride12.

`CampaignHandler` accepts switching map11, sets scenario4, reverses campaign
side, then writes `enabled[scenario][side]` rather than `[side][scenario]`.
The retail addressing explicitly multiplies scenario by12. For valid side0/1
this reaches game+0xd2/0xd3, the first two bytes of the existing unknown
padding. It is outside the enabled subobject but inside the game allocation.
This review neither silently transposes the write nor asserts a demonstrated
gameplay failure. The fixed instruction checks preserve both anomalies as
retail facts. ShowCampaignInfo clamps alternative track widgets to logical
ID11, whereas the updater broadcasts ID12 too; resource/widget behavior is
not inferred from that discrepancy alone.

The win handler scans2x11 enabled maps, chooses the first and otherwise leaves
scenario=-1 before showing the selection dialog. A no-enabled-map state is
not proven unreachable here. Starting/current/view side must remain0/1 and
live map indices valid. PlayPreScenarioSmacker's map+1 and resource switches
assume the campaign domain; they do not sanitize arbitrary signed inputs.
