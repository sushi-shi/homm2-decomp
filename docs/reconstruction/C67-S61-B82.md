# FLY: casts, scalar storage and flight contracts

The complete 476-line TU, all four functions, private enum and duration macro
were read. Parent `d2570cb2`. Declarations belong to `army.h`; there is no
separate FLY header. Real army/hexcell/animation owners, PATH's direction helpers,
the complete adjacency initializer and `BuildTempWalkSeq` were checked as dependencies.

## C67 applied; S61 measured and retained

Six of sixteen written casts are removed from `FlyTo(destination)`:

- Two `i32` coordinate-to-`float` assignment casts: the real float destinations
  already convert `fromX` and `sourceY`.
- Four `i32`-to-`i8` assignment casts: the actual front/rear hexcell side/index
  members already narrow the current army identifiers.

The remaining ten casts expose actual square-root input/output, floating division
and coordinate/timer truncation boundaries. In particular, both parenthesized
step-count conversions are retained: the verified instruction sequences load
two integer operands separately on x87 before division. This audit does not
substitute integer division or change the order of timing precision/truncation.

The C67 coordinate product has four arms and the occupancy product sixteen.
All preserve the original 2530-byte body and normalized ordered relocations.
Their combined retained source also preserves the entire native TU, including
all seven emitted functions, data sections and ordered relocation records.

S61 tests all subsets of three unread locals in each of `ValidFlight` and
`FlyTo` (two eight-arm products). Every nonoriginal subset changes native text;
the latter function shrinks to 2515..2524 bytes. A separate two-arm test removes
the `frameCount0 += WALK_BEGIN_STANDING` store that is overwritten by the later
`frameCount0 = WALK_MIDDLE` assignment. That changes 2530 to 2512 bytes, so the
original store is retained. No fake padding owner replaces these scalars.

All five products completed, 38 arms total, with source restored and no timeout.
[The measured source record](../matching/FLY/casts-and-scalar-storage.cpp)
preserves every arm, hash, elapsed time and topology result. These are independent
source products, not a full cross-product or unchanged-source TU-state census.
Equal diagnostic block counts do not establish equal stack operands or bytes.

## B82: dependencies matter

`CanFit` rejects invalid/front-border/occupied/blocked candidate hexes and may
try the opposite rear cell for a wide unit. Its optional output is set to the
requested hex before validation, then changed only on a successful alternate
fit. Failure does not imply an untouched output; callers must use the return.
All in-tree calls were located in FLY, FINDPATH and SPELLS.

The first rear-cell pointer starts null and is assigned only for valid,
non-border columns. The later dereference rechecks validity but not the column.
Read in isolation, this looks unsafe. However, `SetupAdjacencyArray` maps every
border-column neighbor to -1. Its complete 447 retail bytes/sites/targets pass
independent checking, and the two PATH helpers preserve its signed-byte result.
All 702 positions of the finite 117x6 geometry were enumerated: its 516
nonnegative neighbors are valid, interior-column hexes. Consequently a valid
neighbor passes the pointer-assignment test; there is no proven null dereference
under initialized, unmodified adjacency. The only direct table writes found in
source are the initializer's three assignments. The lifecycle contract remains;
no new guard or padded object is justified by the isolated expression.

`ValidFlight` validates destination and target side/index (two sides, twenty
slots). An invalid target designation takes ordinary fit mode; an assigned
target uses the actual army row. Initial attack-mask traversal has eight logical
bits; the landing loops stop when all six adjacent bits are blocked. For valid
endpoints, the preference helper tries available ordinary directions before
special directions, so those loops do not need an invented direction-array
owner. Current hex, wide front/rear placement, facing and coherent manager/current
army still require their lifecycle contracts. A malformed endpoint can produce
direction -1 before the caller's shift/adjacency access; this is not repaired.

For a wide landing, the loop stores every available attack direction and thus
retains the last one, not the first. If no bit is available it does not initialize
`m_attackDirection` there. The full placement/attack contract must ensure a usable
direction; no assertion of normal-gameplay failure is made. The path-mode-derived
`1 - mode` retry flag is retained as implemented.

`FlyTo(destination)` validates the incoming destination, then may adjust front
and destination by one while changing facing. It subsequently accesses front,
rear and destination hex owners without another range check: the approved landing
and wide-unit placement contracts matter. It updates actual occupant fields and
restores original facing at the tail; these are related coordinate/state phases,
not unrelated variable reuse or member-to-owner recovery.

The square-length multiplication/addition occurs in signed integer arithmetic
before conversion for `sqrt`. Pixel coordinates and derived arithmetic must fit
their intended domains; the cast does not prevent earlier integer overflow.
Flight-speed division occurs only for positive speed, and step count is clamped
to at least one before the two x87 increments. The later `stepCount1 == 0` branch
is therefore unreachable under the local scalar flow; it is preserved retail
structure, not silently removed during a casts/owners review.

Animation storage is real: 34 sequences with sixteen frame bytes per sequence,
plus sixteen walk offsets. `BuildTempWalkSeq` appends source sequences; its own
capacity/data contracts remain those already reported for ARMY. A positive loop
bound protects the animation modulo from a zero divisor on an entered iteration.
It does **not** prove that `frameCount0` (middle count plus the conditional end
count) is positive for the timer divisions. Valid animation data must provide
that denominator. Both timer formulas retain their unguarded floating division;
this is not a claim of an integer divide crash or observed gameplay failure.
Resource lifetimes, combat-speed index, finite timing conversions and screen
rectangles remain caller/data contracts. No text formatter or manual varargs
occurs in this TU.
