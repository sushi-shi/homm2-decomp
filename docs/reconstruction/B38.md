# B38: fixed-width NetBIOS listen from a C-string wildcard

The `NETBIOS_SESSION_LISTEN_ANY` arm passes `gNbListenName` directly to
`nb_listen`. The pointer's only source initializer is `"*"`; no other source
assignment exists. `nb_listen` copies `NETBIOS_NAME_SIZE` (16) bytes from that
pointer into the control block's real 16-byte `callName` field.

Genuine retail confirms the pointer at VA `0x00515c4c` targets `0x00515c5c`.
The 16 bytes starting there are:

```
2a 00 00 00 65 3a 5c 55 73 65 72 73 5c 69 67 6f
 *  NUL padding  e  :  \  U  s  e  r  s  \  i  g  o
```

Thus the destination is large enough, but the source copy crosses the end of
the two-byte literal into alignment and a following source-path literal.
Changing it to a zero-padded 16-byte wildcard would change the actual bytes
copied; it is not a neutral reconstruction cleanup.

`check-function.py SOURCE/netwin 0x74f38` passes all 194 instruction bytes,
complete DIR32 sites and every ordered call/data target against hash-verified
retail (`build/b38-listen-proof.log`). The caller `nb_sess` also passes full
1223-byte/83-target proof including its local switch table (V01). The variable
pointer and fixed copy length are independently visible in that chain. No array
was enlarged and no synthetic storage owner was invented to hide the overread.
This finding is retained as retail behavior; whether the NetBIOS API ignores
the trailing wildcard bytes does not make the C++ source read in bounds.
