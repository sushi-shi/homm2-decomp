# PHILAI purchase and target-selection review

Twenty more consecutive PHILAI bodies, `GetBestBHC` through `TurnsToBuy`, and
the later `CanBuyBHC` consumer now have individual ten-pattern reviews.
The source file is still not fully reviewed. Later partial reads are not
credited as complete functions.

## C49: numeric casts applied

`RVConversion` multiplies seven integer resource quantities by existing float
weights. Ordinary arithmetic already converts each quantity for that product.
All seven operand casts are removed; the final float-to-i32 truncation remains
explicit. Resource order and addition grouping are unchanged.

The complete bounded family consists of128 independent explicit/implicit
operand combinations, plus the original C-style control. Candidate operands
use either `static_cast<float>(p[IDX(resource)])` or `p[IDX(resource)]`; every
candidate keeps `static_cast<i32>(sum)`. This is a cast-style/operand family,
not a search over reassociation or implicit result conversion.

`LikelihoodOfEnemyAttacking` similarly needs no operand cast for
`nAttack * chanceA`; its final i32 truncation stays explicit. Its three arms
are the original two C-style casts, two explicit casts, and the retained
implicit operand plus explicit result cast.

| Function | Completed arms | Elapsed | Bytes / relocations |
| --- | ---: | ---: | ---: |
| RVConversion | 129/129 | 127.932s | 113 / 8 |
| LikelihoodOfEnemyAttacking | 3/3 | 3.602s | 84 / 1 |

Every arm is exact under the matrix's strict byte/size/ordered-relocation
check, with identical text and normalized-relocation hashes within its family.
Both matrices finish without truncation and restore their source. Artifacts
are `build/c49-{rv,likelihood}-{axes,manifest}.json` and the respective
`-batch/results.json`. Both final bodies pass `check-function.py` independently
against the genuine retail image. The final full build and the before/after
native comparison pass: all89 emitted PHILAI functions, all allocated sections
and ordered relocations/addends remain identical.

This removes eight written casts and replaces two C-style result casts with
explicit C++ casts. It does not remove real precision boundaries in the larger
value/odds routines.

## U16: purchase descriptor retained

The full lexical producer/consumer set is now read: CheckBuyStuff, GetBestBHC,
GetBestBuilding, GetBestCreature, GetBestHero and CanBuyBHC. `BHC` is a real
tagged descriptor: its building arm carries a building enum; its integer arm
carries an available-hero slot or a dwelling slot. The quantity is consumed
only for creature purchases. The union is retained; replacing it with raw
bytes or a single untyped integer would lose useful type information.

Building/hero producers leave the irrelevant quantity field uninitialized;
descriptor assignment copies it, but no reviewed non-creature consumer uses
it. Separately, GetBestBHC logs `best.type` and `best.what` before setting NONE
when no candidate was selected. With no eligible town, CheckBuyStuff's local
descriptor does not supply initialized fields. This is an initialization
contract, not evidence for a bigger aggregate or an authorized retail behavior
change.

## B70: resource limits and movement producer

`MaxBuyableCreatures` (`0x83e81`) passes all130 ordinary bytes, complete DIR32
sites and ordered targets. Its local result at `[ebp-4]` is overwritten on
every one of seven resource iterations:

```text
+0x27  cmp [ebp-0x24], 7
+0x37  mov [ebp-4], 9999       ; zero cost
+0x66  idiv [ebp+4*esi-0x20]   ; positive resources
+0x6a  mov [ebp-4], eax
+0x6f  mov [ebp-4], 0         ; no available resource
+0x76  jump to next resource
+0x78  mov eax, [ebp-4]       ; return last iteration only
```

There is no minimum accumulation. The last resource is gold. However,
`CanBuyBHC` (`0x88284`) passes all279 bytes/sites/ordered targets and independently
checks every resource cost before approving a creature purchase. This limits
what can be inferred: the helper may propose a quantity that is then rejected,
but this alone does not prove an actual overspend. Neither loop is rewritten
to change retail behavior.

DetermineTargetPosition's first branch calls GoodAdjacent. On success it
writes both target coordinates and the returned direction, then returns1000.
It therefore supplies the special-direction path identified in B69. The
GoodAdjacent consumer chain is now source-complete for that transition:
valid adjacent movement, selected event value above100 and success chance
above80 lead to the direction output. No gameplay execution has been recorded.

GoodAdjacent passes all713 bytes/sites/ordered targets. DetermineTargetPosition
passes all3430 ordinary bytes and DIR32 sites; the fixed-site
`check-ai-movement-constants.py` supplement proves its seven remaining private
double operands. The same supplement proves DoAI's four private doubles,
closing that earlier operand-evidence gap without relaxing the general checker.
It requires exact site, destination, zero addend, width and payload at each
operand. Logs: `build/ai2-movement-constants-final.log`,
`ai2-adjacent-retail.log`, `ai2-81c03-retail.log` and the earlier DoAI retail log.

Other B70 entries retain valid player/town/hero/creature/building/path domains,
nonzero ratio denominators, initialized cost outputs, float representability,
and debug formatter input bounds. `%18s` and `%8.2f` widths are minima, not
capacity limits. The legitimate72-town and seven-resource arrays are not
reclassified as artificial stack aggregates.
