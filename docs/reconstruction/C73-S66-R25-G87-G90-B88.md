## B88: concrete bounds and failure conditions

GetMapHeader reads420 bytes into the real420-byte header, but checks neither
read result nor magic, dimensions, enum fields or string termination. Successful
open returns1 even after a short/error read. InitializeFiles ignores that result
on both scans and when filling the final header array. Missing/truncated files
can therefore feed uninitialized or stale header fields into filtering/display.
Map names60 and descriptions300 fit gText768 only if terminated; difficulty
must be0..4 and all other resource-frame/condition domains must be valid.

InitializeFiles counts, allocates, then enumerates again without an insertion
capacity check. Names/extensions have count+1 slots but headers only count:
even one newly accepted map can exceed header capacity. A shrinking/changing
set can leave unused/uninitialized headers while m_fileCount remains the first
count. CountOnly also writes m_fileCount. MapExistsForFilter restores the global
filter but not that member, so a failed filter query can leave a different count
attached to the old arrays. Stable enumeration and state coherence are real
preconditions, not inferred from the pointer types. Allocation-size arithmetic
and memory exhaustion are likewise not repaired in this audit.

Win32's actual cFileName[260] bounds terminated API names to259 characters,
which fit nameBuffer352, name slots351 and recombined fullPath300. Extensions
must include a dot and fit four characters plus NUL: no-dot input leaves the
local extension uninitialized or stale, and an overlong suffix can overflow
its five-byte buffer. Attributes are not checked to exclude directories. The
in-tree filename patterns constrain ordinary suffixes but do not validate an
arbitrary public InitializeFiles call. Map-mode reads use gcMapPath, not the
passed enumeration directory, so those must agree.

at+0x2b3. GetMap and PickLoadGame pass the entire `*.MP2`/`*.MX2`/`*.GM?`/

lands in m_filename[0]. These two distinct addresses and the unchanged copy
are in retail. This is a cross-subobject write within the complete0x42f-byte
requester, not a reason to enlarge the five-byte field or report an outside-
allocation write. SaveGame passes a proper four-character suffix plus NUL.
The caller and destination evidence is retained; no source-layout repair is
justified that would erase this behavior.
