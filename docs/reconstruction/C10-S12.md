## C10: a real static-text ownership mismatch

The explicit const_cast is required by the modern interface: gStatNames holds
read-only text while the textWidget constructor accepts an owned mutable
pointer. `check-early-api-syntax.py` confirms that removing this cast produces
exactly one C++20 constructor error; both retained dialects pass. Recasting
the catalog or moving a cast into the constructor would not repair ownership.

The source and retail operands establish this normal path:

```text
gStatNames[0..2] (image strings)
  -> textWidget::m_text at +0x20 (stored directly, not copied)
  -> resource window closes its owned widgets
  -> virtual deleting destructor
  -> operator delete(m_text)
```

The first three catalog pointers are00506d08,00506d10 and00506d18; they point
to complete6-,7- and11-byte terminated image strings, not heap allocations.
The unused fourth choice is a7-byte string at00506d24. DoArenaDialog's
three-entry loop uses only the first three table entries.

At DoArenaDialog+25b, the table operand resolves to004fdc80; the constructor
call operand at+27a resolves to004c2fe0. The constructor's exact bytes at+6a
are `8b 4d 18 89 48 20`: load the supplied text argument and store it directly
at this+20. There is no text-allocation or duplicate call in that constructor.

The resource-window constructor unconditionally sets OWNS_WIDGETS: at
004ba700+103 it emits `80 ce 40` (set bit4000), then stores the flags. Normal
DoDialog exit calls RemoveWindow, which calls Close. Close tests4000 and
calls the virtual deleting-destructor slot at vtable+4. The textWidget slot
at004ea9a4 points to004c2fb0, whose direct call reaches004c31c0. That destructor
loads the same text member (`8b 48 20` at+43) and calls operator delete at
004d68c2 (REL32 operand+4e).

These facts expose a retail static-pointer deletion/ownership-contract defect.
They do not establish a particular observed crash: allocator behavior and
runtime corruption were not exercised. No allocation, copy, ownership flag,
runtime guard or destructor behavior is silently changed to hide it.

`check-arena-text-ownership.py` reproduces the fixed operands, image strings,
flags, vtable slot and deleting-helper calls against the hash-pinned retail
image (`build/c10-ownership.log`). Full generic retail checks pass for
Window::Close160 bytes, manager RemoveWindow233 bytes and DoDialog409 bytes.
The arena, textWidget constructor and destructor checks preserve all
ordinary bytes/targets but still have the known private EH handler/FS-slot
limitations. The resource-window constructor has the same limitation.
The generic deleting-helper checker also encounters duplicate COFF symbol
records; its two actual call operands are checked explicitly instead. These
are scoped ownership proofs, not a claim that those exception graphs are
fully certified by the generic helper.
