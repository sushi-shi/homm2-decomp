# C18: native DirectPlay output types

`dpProcessMessages` now declares `sender` and `to` as the SDK's `DPID` type,
matching the two `LPDPID` outputs of `IDirectPlay::Receive`. This removes both
pointer reinterpretations and the later conversion of `to` back to `DPID`.
The pinned SDK defines `DPID` as `DWORD`; both locals still occupy four bytes.
The existing signed game-level sender boundary is unchanged.

A complete four-arm matrix independently selected the original `i32` or
actual `DPID` owner for each output. All4 arms compiled in2.60 seconds and
kept the152-byte function/14-block topology. The generic runner rejects
private target identities even for its baseline and reports raw sibling
identity changes for the typed arms. The independent native comparison
resolves those diagnostics: after established compiler-private normalization,
**all19 emitted functions and every allocated section are identical**, including
ordered relocation sites, types, owner identities and addends.

`check-function.py SOURCE/dpnetwin 0x36e9b` also passes exact instruction bytes,
size, complete DIR32 sites and every ordered retail target against the pinned
genuine image. No fake compiler state or ABI shim is retained.

Artifacts: `build/c18-{axes,manifest}.json`, `build/c18-batch/results.json`,
`build/c18-before-after.log`, `build/c18-retail.log`. Native comparison uses
`build/c18-dpnetwin-before.obj` and `build/objdiff/base/SOURCE/dpnetwin.obj`.
The complete source arms are recorded in
`docs/matching/dpProcessMessages/typed-player-ids.cpp`.
`homm2 build` and all877 selftests pass (`build/build-dpid.log`,
`build/selftest-dpid.log`). This changes output ownership, not the DirectPlay
receive-length and player/session-bound concerns.
