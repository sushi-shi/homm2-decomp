# U06: actual army type and count arrays

Removed both armyGroup unions. The runtime owner now has five creature-type
bytes and five signed16-bit counts, with no duplicate type/count names and no
unsigned alternate view. All86 alternate-member accesses across24 functions
use the existing m_creatureTypes/m_creatureCounts fields. Two compensating
signed casts in map initialization are also removed.

## Signedness and ownership

m_quantities and m_creatureCounts were identical i16 arrays; m_troopTypes and
m_creatureTypes had identical enum/storage types. Those changes are same-type
member consolidation. The unsigned m_troopCounts alias had only six uses:
four stores and two loads immediately converted to i16 before comparison.
There was no unsigned arithmetic, unsigned comparison or escaping u16 pointer
through that alias. The final header/source census finds none of the three
removed member names.

The mapHeroExtra/mapTownExtra troopCounts fields remain u16 serialized inputs.
Only their15-byte runtime army destination changes representation ownership.
VC6 still copies the same low16 bits and tests the same signed value, including
0x8000..0xffff. No invalid count is reinterpreted as a positive army size, and
no file validation or gameplay correction is added. Existing later negative
count normalization in CheckHeroConsistency is unchanged.

The record remains15 packed bytes: types5 at0, counts10 at5. Containing hero
and town records remain250 and100 bytes. `army-group-layout-probe.cpp` proves
those layouts under the actual VC6 compiler; `check-army-group-layout.py` also
checks all three changed TUs plus ARMYGRP in both C++98 and C++20. Its reference
binding verifies that the final count element is genuinely i16, not an unsigned
field hidden behind a read cast. All checks pass (`build/u06-layout-dialects.log`).

## Measured cast removal and verification

The structural owner change first passed a full build and strict98-object
native comparison against38c69043 (`build/u06-owner-native.log`). Then two
complete two-arm products tested the remaining signed casts independently:

- u06-town-signed-count: both2161-byte SetupTowns arms have identical text and
  normalized relocations,116/116 diagnostic blocks;3.203 seconds.
- u06-hero-signed-count: both1830-byte ProcessOnMapHeroes arms have identical
  text and normalized relocations,81/81 blocks;3.327 seconds.

Both products restored source, completed without truncation and retained the
direct signed load. Exact axes/results are archived in `docs/matching/army-group/`.
No generated state declarations or additional casts are retained.

The final combined change passes all98 native objects/1826 emitted functions,
all allocated-section bytes/attributes and complete ordered relocation graphs,
with no added owner/type/addend exceptions (`build/u06-final-native.log`).
The full build passes1727/1727 function checks and291987/291987 data bytes
(`build/build-u06-final.log`).

All24 changed functions independently match their retail ordinary bytes and
sizes. Ten also fully pass the general DIR32-site/ordered-target checker,
including both cast-removal targets. Thirteen retain existing private-float
identity gaps; ViewArmy retains its four EH/FS-relative gaps. No general checker
rule was relaxed. [Every changed function and its exact retail result](U06-functions.tsv)
is recorded separately; the full unchanged native graph proves this recovery
even where the general retail checker remains partial.

Army-slot validity, creature domains, allocation/lifecycle, loaded counts and
combat/map protocol consistency retain their previous per-function bounds
contracts. This change does not manufacture extra storage for malformed data.
