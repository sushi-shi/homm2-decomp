# B24: world-map horizontal clamp writes the vertical origin

This is retail-confirmed behavior, not a reconstruction typo to silently fix.
The initial radar-click branch checks the horizontal origin but stores its
clamped value into the vertical origin. The later drag loop clamps the correct
axis. Both are currently reproduced by the source.

```
004af866  8b 0d a4 3f 53 00  mov ecx,[iVWMapOriginX]   ; 00533fa4
004af86c  03 0d b0 3f 53 00  add ecx,[iVWViewableCells]
004af872  3b 0d 98 8b 4f 00  cmp ecx,[MAP_WIDTH]
004af878  7c 12              jl  004af88c
004af87a  8b 15 98 8b 4f 00  mov edx,[MAP_WIDTH]
004af880  2b 15 b0 3f 53 00  sub edx,[iVWViewableCells]
004af886  89 15 a8 3f 53 00  mov [iVWMapOriginY],edx   ; 00533fa8
```

Verified control SHA-256:
`bc7e9c9320aa3e5c1ffca6d2bfa530ecedb5a3bca1b91c959501c15ad72c329a`.
X is at `0x00533fa4`, Y at `0x00533fa8`, and viewable count at `0x00533fb0`.
These are the restored source claims; earlier addresses from the rejected
reconstructed image were wrong. Thus the
store is genuinely to the wrong axis, not a mistaken name inferred only from
this handler. `VWCompleteDraw` immediately uses the unclamped horizontal
origin in its map-cell loops.

No behavior change is applied: fixing that store would diverge from retail.
Map/index domains and other bounds questions remain visible in the per-function
ledger rather than being hidden behind the matching source.
