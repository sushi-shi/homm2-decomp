arguments of the two background-icon constructors; their real parameter

`CASTLE_SLOT_COUNT` in handler ID-range tests are also redundant. The seven
remaining `BuildingSlotType` casts narrow an intentionally mixed building/

no truncation, failed compile or timeout. These are not a cross-family or
TU-state product. Every arm is preserved as an exact source span and explicit

## B84: capacities, indices and producer contracts

The eighteen-byte `castleSlotsBase` is a real building-slot table. The only
source writes to `castleSlotsUse` are SetupCastle's copy/upgrade/Warlock
alternative branches. Exhausting their outcomes from the retail initial table
gives values 0..30: valid bit-shift positions, nineteen neutral-name entries or
twelve dwelling entries in each of six faction rows. This depends on initialized,
unmodified tables; arbitrary memory corruption is not covered.

The handler's three widget-ID intervals bound the decoded slot to 0..17.
Captain/formation controls bypass that lookup, and the two switches gate actual
building shifts/API calls. `whichBuilding` changing from a slot index to its
building ID is one decoding operation, not a fabricated union or owner cast.
Both functions use real `tag_message` widget views; ConvertToHover supplies the
handler's hover-message representation. No manual argument-slot varargs,
member-to-owner subtraction, fake stack array or artificial out-of-object
pointer occurs.

[The pinned retail checker](check-castle-text.py) verifies these local bounds,
including NUL:

- Both castle/portrait icon filenames need 13 bytes, within the real 16-byte
  filename buffer. The fixed captain `%c` filename also needs 13 bytes.
- Captain stat scratch needs at most 13 bytes even allowing arbitrary signed
  32-bit numeric values, within 200. The complete name list needs 32 bytes and
  the numeric list at most 49, within the 768-byte global buffer.
- All sixteen status formats fit 768; the largest conservative bound is 52.
  All building-name sources, including the shrine override and six real
  dwelling rows, were checked; maximum name length is 20 bytes.

The complete 105-byte `GetBuildingName` producer passes independent retail
byte/site/target checking. This retail translation's recruit format, entry11,
contains **no directives**. Its supplied hero-name and alignment arguments
therefore do not lengthen the text, but their expressions still evaluate and
require valid available-hero IDs, hero records and alignment indices. They
were not deleted as part of this casts/owners audit.

The `CannotRecruitHero` helper rejects hero counts **at least** eight, while
SetupCastle's display and the hover text test equality to eight. These are
actual retail predicates. Normal roster bounds reconcile them; this review
does not silently change their malformed-state behavior. Its sole inlined
call is covered by the complete handler proof; no standalone function address
is invented for it.

Remaining contracts: live town/player/window/bank/resource owners, six-faction
indices, available hero IDs, valid map coordinates and terrain-image indices,
eligible icon frames, town-object count at most32 and valid object pointers,
and timely consumption/copying of text passed through widget messages. The
normal background loops use real coordinate/frame scalars; parameter conversion
does not substitute for resource bounds or rendering clipping.
