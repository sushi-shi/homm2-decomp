# Save transfer and diff-file bounds: inherited defects

These findings are verified against the pinned genuine retail executable.
No packet-length change, extra zero-fill, invented padding, or copy-length
correction has been applied to the byte-matching reconstruction.

## B62: acknowledgement tail is not initialized

`game::ReceiveSaveGame`, RVA`0x5e236`, allocates256 bytes for `ackBuffer`.
For an acknowledgement request it copies100 tracking bytes into offsets0..99,
then calls `TransmitRemoteData` with length200. Nothing initializes offsets
100..199 in this function. This is not an allocation overread:200 fits256.
It transmits unspecified allocation contents, not a proven particular secret.

Function-relative retail bytes (identical in the candidate):

| Site | Bytes | Meaning |
|---|---|---|
| `+0x1c4` | `68 00 01 00 00` | allocate256 |
| `+0x3b7` | `83 c1 64` | acknowledgement loop ends at start+100 |
| `+0x3e2` | `88 0a` | copy one tracking byte |
| `+0x419` | `68 c8 00 00 00` | transmit length200 |

The allocation is plain `new u8[size]`, without value initialization.
`TransmitRemoteData` (`0x8dcc0`) copies the supplied length into its message
payload and sends length+9 bytes when networking is active and setup is over.
Its early return when networking is disabled does not initialize this tail.
The sending game's acknowledgement consumer examines at most100 response
bytes, the actual packet-batch size.

Independent function checks prove all1736 receiver bytes and466 transport
bytes, complete DIR32 sites and ordered targets:
`build/game-army-5e236-retail.log`, `build/b62-transmit-retail.log`.
Disassembly is `build/game-army-5e236-asm.log`; the receiver's loop/call
operands are at the offsets above. Sending100 instead, or initializing the
extra bytes, would be a behavior-changing fix requiring a separate remit.

Other unresolved contracts remain: signed packet numbers, at least two
payload bytes before reading the index, actual packet payload length, the
5000-entry tracking arrays, encoded-size allocation products, and the700000-
byte decode buffer. Received CRCs are computed and logged but not compared
to the expected values. No successful integrity check is inferred from that
logging. The receiver does not locally constrain command packets to the
specified sender.

## B63: terminal diff copy uses the old-file remainder

`CreateDiffFile`, RVA`0x5f47a`, allocates `fullData` with `joinSize` bytes.
When either input reaches its end, it sets `length = oldSize - position`,
then copies that many bytes from `fullData + position` into the output.
The whole1363-byte function, complete DIR32 sites and ordered targets agree
with retail (`build/game-army-5f47a-retail.log`).

The disassembly establishes `oldSize` at ebp-0x10 from the old-file `FileSize`
call and `joinSize` at ebp-0x3c from the new-file size. `fullData` is ebp-0x38.
At `+0x29b`, `8b 45 f0` reloads oldSize; `+0x29e`, `2b 45 fc` subtracts
position. The resulting length is pushed at `+0x2b9`; the source loaded
from ebp-0x38 is advanced by position and passed to `memcpy` at `+0x2c8`.

Consequences of that measured length rule:

- Old8/new4 with a common four-byte prefix: after the matched run, position4,
  then length4 is copied from the new allocation's one-past pointer.
- Old4/new8 with the same prefix: after position4, length0 ends encoding,
  omitting the four-byte new tail.

These are source/retail-derived length counterexamples, not runtime crash
tests or proof that an ordinary valid save necessarily triggers either case.
The full-send branch bypasses this differential path.

The separate output bound `max(oldSize,joinSize)+5000` still needs an encoded-
overhead argument. `CreateJoinFile` additionally requires a complete two-byte
header, valid encoded lengths and an output no larger than700000; malformed
skip/copy commands are not locally checked. Those questions are not resolved
by proving this one terminal-copy defect.
