# B54: sudden-exit packet carries two uninitialized bytes

`HandleRemoteSuddenExit` (`0x0046ece2`) transmits a real seven-byte
`SPlayerExit` record after assigning only its first five fields.
Independent genuine-retail checking passes all 142 bytes, all DIR32 sites and
every ordered target (`build/kb-clean-0x6ece2-retail.log`).

Retail and the current VC6 output agree on every field store:

| Function offset | Instruction | Packet field |
| --- | --- | --- |
| `+0x21` | `88 45 f4` | `netPosition`, byte 0 |
| `+0x2a` | `88 4d f5` | `gamePosition`, byte 1 |
| `+0x33` | `88 55 f6` | `updateNetworkControl`, byte 2 |
| `+0x36` | `c6 45 f7 00` | `timedOut`, byte 3 |
| `+0x3a` | `c6 45 f8 00` | `eliminated`, byte 4 |
| `+0x69` | `6a 07` | Send all seven bytes |
| `+0x6e` | `8d 4d f4` | Pass the record at `[ebp-0xc]` |
| `+0x71` | `e8 …` | Call `TransmitRemoteData` at `0x0048dcc0` |

There is no store to bytes 5/6 (`hostReported`/`continueGame`) before this
call. They are named protocol flags, not unused padding. The current receiver
only consults `hostReported` on the eliminated-player path, so this evidence
does not by itself demonstrate an erroneous branch at the peer. It does prove
that the sender supplies two uninitialized stack bytes to transmission.

Do not conflate `HandleRemoteDeadPlayerExit`: it leaves `continueGame`
unset initially, but its local call to `ReceiveRemotePlayerExit` enters the
eliminated branch and sets that field before subsequent use/transmission.
The separate source and per-function reviews record that distinction.

No synthetic padding, smaller packet, or byte-changing initialization is
applied. Retain the wire layout and report the genuine retail behavior.
