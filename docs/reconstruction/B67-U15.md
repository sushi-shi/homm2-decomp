# Town state and spell-owner contracts

All TOWNMGR and TOWN function bodies, including the manager's inline setter and
town's inline occupant getter, have individual ten-pattern reviews. These
contracts remain distinct from the text-capacity proof in B66.

## B67: state-dependent accesses

Town-object construction indexes the6×32 building-info table before testing the
building sentinel. Its callers must supply an actual building, not -1. Rendering
also requires live icons and enough frames for the faction's build state and
animation count. The32-entry ordering rows bound normal object creation; their
NONE entries are skipped. Reusing that population for another town of the same
faction requires the old view to be intact.

The manager assumes its selected/pending/swap strips and their armies are live,
with slots0..4 and valid creature IDs. SetupTown deliberately creates a strip
with a null army for a captain-only or empty hero panel. SetCommandAndText
guards null army in one selection branch, whereas Main's right-click branch
does not. Whether normal UI resources can deliver that selection remains an
unresolved caller/resource question, not a proven gameplay crash.

BuildObj initializes its lookup result to -1 and uses it if no object matches.
It also dereferences constructed borders without checking null. These are
construction/caller contracts. The six faction tables, building shifts0..31,
five mage levels, twenty spell slots and twelve dwelling slots are real domains;
arbitrary numeric messages/debug input do not establish them. BuyBuild's mage
cost index is actually clamped in its table expression, unlike KB's B51 helper.

RecruitHero requires available slot0..1, a valid hero ID, room in the eight-entry
hero list and an available map/town location before appending. Its temporary
owner value is preview state and is restored or retained according to the
dialog result. It is not an unrelated scratch variable.

SplitArmyHandler's upper clamp is `maximum-1`; maximum must be positive.
For maximum0, a selected text amount can become -1 despite its preceding lower
clamp. Decimal parsing also needs terminated representable input. These are
source-derived preconditions, not changes justified by the byte-matching task.

Town::Deallocate requires a valid owner, nonempty town list and the current ID
to occur in that list. If it does not, its search result remains -1 and feeds
compaction; an empty list also makes the final store use index -1. No negative
index or extra padding was introduced by this audit, and no runtime-reachability
claim is made from those counterexamples alone.

Thieves-guild ordering requires playerCount≤6, matching live/dead counts and
initialized category statistics. Its dead-player skip loop relies on those
counts rather than testing another explicit upper bound. Growing one scratch
array would not repair corrupt state across the companion arrays and players.

## U15: overlapping town spell/count owner — untried structural recovery

The packed100-byte town has a union containing20 spell bytes and a second view
with a19-byte prefix followed by six count bytes. Thus count0 aliases spell19;
actual count1..5 are the five bytes immediately following the20 spells.

The complete lexical consumer list is:

- TOWN.cpp: GiveSpells and BuildBuilding;
- TOWNMGR.cpp: SetupMage and MageGuildHandler;
- GAME.cpp: SetupTowns;
- PHILAI.cpp: HeroInteractionAtTown.

No current reference reads or writes count0, nor the prefix by name. GAME also
uses the flat spell view, so that flat/2D union cannot simply disappear without
changing its consumers. A credible candidate is a20-byte spell union followed
by five zero-based count bytes, adjusting every count index. This would remove
the artificial count overlay/prefix without changing the100-byte serialized
layout or any real field location.

That candidate is **UNTRIED**. The count consumer in PHILAI has been located and
its spell loop inspected, but the entire PHILAI function has not yet received
the ten-pattern review. Full consumer review, byte/ordered-relocation checks in
all four translation units and the shared-layout gates are required before
retention. A01's clearer MageGuildHandler indexing does not count as U15 closure.

## Remaining source-shape findings

C46 covers bounded ID/coordinate conversions, crest constants passed through
i8 to an i32 parameter, and the timer conversion. Real CP1251 unsigned-byte
comparisons stay unsigned. R10 covers a count/type swap temporary and indices
reused across hero/town/artifact/primary-stat roles. G55/G56/G57 track eight
building-info joins, three split-amount joins and four thieves-rank joins.
These need their own complete structural/source matrices.

S48 records unread UI-control locals, the unused crest-frame computation,
unconsumed call results and oversized stat-line scratch. GetHero and other
calls are not erased just because a result is unused. Likewise SetupMage's
misleadingly named `unusedGuildFrame_g` is consumed by a message and is not dead.
Unknown persistent layout fields remain real storage claims, not deletable gaps.
