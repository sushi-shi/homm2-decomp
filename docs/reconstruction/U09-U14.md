# U09/U14: shared save headers and complete packet owners

Base commit: `3e738b4bd`. This follow-up implements the typed-packet question
left open in [C44/G50/S43](C44-G50-S43.md), removing eight further pointer casts.
The network API, allocation sizes, sent lengths, cleanup and validation
behavior are unchanged.

## Recovered owners

| Owner | Retained layout and use |
|---|---|
| RemoteSaveInitialization |16 bytes: dataSize at0, crc at4, wireCrc at8, playerExited at12 |
| RemoteSaveChunk |247 bytes: signed index at0, 245 data bytes at2 |
| RemoteSaveBuffer |256-byte sender allocation; real initialization/chunk/raw-byte union |
| RemoteSaveMessage |256 bytes; common9-byte envelope and247-byte receive payload |
| AdventureRemotePayload |247 bytes, replacing the undersized16-byte view |
| KbRemotePacket |256 bytes, replacing the partial221-byte view; payload.data grows1 to247 |

The four-word initialization record is shared by the sender,
CheckHandleNet and WaitForOtherPlayer. The latter's old names saveId,
saveOffset and saveSize actually represented data size, file CRC and wire
CRC. Its unused fourth word is still part of the same initialization
message. The adventure consumer uses that word as the player-exit flag.
The original i32 storage and raw flag value are preserved.

The sender still allocates256 bytes and sends data chunks of at most200
bytes plus a two-byte index. Its member accesses replace six pointer casts
and a byte-offset expression. The receiver now converts the transport
pointer once to RemoteSaveMessage and uses its chunk fields, removing two
primitive-index casts and its byte-offset expression.

The physical245-byte data capacity is deliberately distinct from the
sender's200-byte chunk limit. RemoteMessage has247 payload bytes after its
nine-byte envelope; the index occupies two. A200-byte data member would
understate the receiver's accessible storage for a longer payload even
though ordinary sender packets use only200. No extra allocation or padding
is invented, and no new received-length check is added.

AdventureRemotePayload retains its real tagged save, SPlayerExit and byte
views. Its byte view must cover more than16 bytes: the map-change consumer
copies four eleven-byte records (44 bytes), and chat accepts a terminated
text payload. KbRemotePacket's one-byte data member was likewise only an
incomplete tail claim. Both now cover the transport's actual247-byte payload.
The212-byte startup record,16-byte save header and7-byte exit record all fit.
KbRemotePacket also names the common envelope's id and payloadSize fields
at offsets1 and7 instead of treating them as reserved bytes.

## Consumer and boundary review

Both complete transfer bodies, CheckHandleNet, WaitForOtherPlayer and the
complete290-line PopNetBox loop were reread. The transport send/dequeue,
44-byte map-change consumer, sender call sites and exit handlers establish
the shared wire meanings. GetRemoteData copies256 bytes from its queue into
the returned transport storage; these are received-buffer views, not claims
that a short packet initialized all256 bytes.

The chat input loop sends at most94 bytes including NUL. Map changes require
44 initialized bytes. These valid-source bounds do not validate arbitrary
incoming strings or payload lengths. Sender mapping, packet lengths,
termination, message initialization and peek/dequeue lifetime remain
contracts. PopNetBox's formatting and truncation issues are unchanged.

CheckHandleNet initializes six SPlayerExit input fields on its save-exit
path. The seventh, continueGame, is not initialized there; the eliminated
branch in ReceiveRemotePlayerExit overwrites it before using or forwarding
it. No dummy initialization was added to make the record appear fully set.

The raw GetRemoteData/TransmitAndWait and codec interfaces still require
their real boundary conversions; those wider API questions remain C44.
The [B62 acknowledgement tail and absent CRC comparison](B62-B63.md) are
unchanged. G50/S43's earlier measured cleanup/storage decisions remain valid
records for their source parent; this change does not claim new structural
search coverage for those families.

## Experiments and proof

First, the shared initialization header and complete adventure/KB payload
views were installed as a byte-evidenced structural recovery. The full
build and all98 native-object comparisons passed before the transfer
source products were run.

The final source products each have three arms:

- Sender: original raw owner, typed owner retaining obsolete word-index
  constants, and typed owner removing those constants. The last is retained.
- Receiver: primitive prefix casts, a typed chunk view at each access, and
  a typed message at the transport boundary. The last is retained.

All six arms compile, restore source and finish without generator or
wall-time truncation. All preserve their baseline bytes and normalized
relocations. These trials used the initial data[200] chunk declaration;
the subsequent physical-capacity correction to data[245] is separately
verified in the final full-build/native/layout/retail checks. No AST or
TU-state census is claimed. Source matrices and retained definitions are
archived in `docs/matching/remote-save-ownership/`.

Earlier diagnostics remain explicit: the first sender matrix had two
compile failures because the local transmitCrc macro also rewrote the
member name. The member was corrected to wireCrc without changing local
names or retaining macro workarounds. The first receiver run reported a
generator cap; it was rerun with sufficient headroom. The repaired
intermediate three-arm sender/two-arm receiver products all compiled and
matched, before the fully typed receive-message alternative was added.
Only the final untruncated products are the source-choice certificate.

Final verification preserves all98 native objects:1826 emitted function
instances, all allocated bytes/attributes and complete ordered relocation
graphs, without exceptions. The full build exits0 with1727/1727 functions
and291987/291987 data bytes. The VC6 layout/type probe passes, as do all94
affected native-TU include closures in both C++98 and C++20.

Eight independent checks pass complete ordinary retail bytes, sizes,
DIR32 sites and ordered targets: TransmitSaveGame1971, ReceiveSaveGame1736,
CheckHandleNet501, WaitForOtherPlayer217, ProcessIncomingGroupMapChange167,
TransmitRemoteData466, GetRemoteData221 and ReceiveRemotePlayerExit713.

PopNetBox's2853 ordinary bytes agree, but its narrow checker still rejects
the private handler at+6 (retail VA0x004e8617) and __except_list operands
at+c,+14,+b1b. The same failures are reproduced against the before snapshot.
Those FS-relative operands are not ordinary image DIR32 sites. This is a
baseline checker limitation, not a newly certified EH graph; no checker
was relaxed. The whole-object comparison includes unchanged exception
machinery and allocated relocation graphs.
