# B46: new-turn widgets lose a tracked reference, not their parent owner

`UpdBottomViewNewTurn` creates week/month and day text widgets, adds both to
the adventure window, and stores both successively in secondary widget slot0
with ID2100. The second assignment overwrites the first tracked reference.
U08 preserved that behavior while recovering the actual widget-pointer array.

The parent list provides an important distinction:

- `heroWindow::AddWidget` links every supplied widget by z-order; it neither
  rejects nor replaces another widget with the same ID.
- `ClearBottomView` explicitly removes and deletes only non-null pointers
  retained in the two12-element arrays. The week widget is no longer there.
- The resource-based adventure window constructor sets `WINDOW_FLAG_OWNS_WIDGETS`.
  Adventure shutdown calls the window manager's `RemoveWindow`, which calls
  `heroWindow::Close`. That method walks the remaining list, removes each
  widget, and deletes it when the ownership flag is set.

Consequently, the first week widget remains linked after bottom-view clearing
and can accumulate across new-turn displays until the adventure window closes.
It is not established as a permanently unreachable heap allocation: the
parent still owns it and normal window closure releases it. Exact rendering
consequences have not been exercised at runtime.

Independent genuine-retail checks pass all bytes, sites and ordered targets
for `AddWidget`265 bytes, window `Close`160 bytes, and window-manager
`RemoveWindow`233 bytes (`build/b46-{addwidget,windowclose,removewindow}-retail.log`).
The U08 before/after whole-build comparison covers the creator and clearing
code, with its independent creator EH limitation documented in [U08](U08.md).

Disposition: retain and report the lifetime asymmetry. Moving one widget to
another slot or changing deletion policy would alter observed behavior and
requires a separate behavior-changing patch, not invented owner padding.
